# Ответы на вопросы - ПР1 (Работа с Git)

## 1. Три основные области работы с файлами в Git и чем они отличаются 

- **Рабочая папка (Working Directory)** - текущие файлы на диске, с которыми я работаю.
- **Индекс (Staging Area)** - промежуточная область, куда попадают изменения после `git add`; то, что попадет в следующий коммит.
- - **Репозиторий (Repository)** - база данных Git, где хранятся все зафиксированные коммиты (история версий).
 
  - Отличие: рабочая папка - "черновик", индекс - "подготовлено к фиксации", репозиторий - "зафиксировано навсегда".

 ## 2. Что происходит при выполнении команд

 - `git add` - добавляет изменения из рабочей папки в индекс (staging area), подготавливая к их к коммиту.
 - `git commit` - создает снимок (snapshot) содержимого индекса и сохраняет его в репозиторий с сообщением.
 - `git push` - отправляет локальные коммиты в удаленный репозиторий (например, на GitHub).

## 3. Почему важно писать информативные сообщения к коммитам 

Информативные сообщения помогают: 
- понять, что и зачем менялось, без чтения кода;
- быстро найти нужный коммит в истории (`git log`);
- работать в команде: коллеги видят смысл изменений;
- откатывать изменения осознанно.

Сообщения вида "update" или "исправление" бесполезны - они не несут смысла.

## 4. Чем отличается `git add имя_файла` от `git add . `?

- `git add имя_файла` - добавляет в индекс только указанный файл.
- `git add . ` - добавляет все измененные и новые файлы из текущей директории и поддиректорий.

Лучше использовать `git add имя_файла`, когда нужно закоммитить только часть изменений (атомарные коммиты). `git add . ` удобен, когда все изменения логически связаны и должны попасть в один коммит.

## 5. Что показывает `git status` и как меняется ее вывод? 

`git status` показывает: 
- текущую ветку;
- какие файлы изменены, но не в индексе;
- какие файлы в индексе (готовы к коммиту);
- какие файлы не отслеживаются (untracked).

Вывод меняется:
- **до `git add`** - файлы в разделе "Changes not staged for commit" / "Untracked files";
- **после `git add`** - файлы в разделе "Changes to be commited";
- **после `git commit`** - "nothing to commit, working tree clean".

## 6. Для чего нужна команда `git remote add origin URL` и что означает слово "origin"?

Команда связывает локальный репозиторий с удаленным по указанному URL и дает ему имя (по умолчанию `origin`).

`origin` - это просто псевдоним (алиас) для URL удаленного репозитория. Можно было бы назвать иначе, но `origin` - общепринятое имя для основного удаленного репозитория.

## 7. Зачем нужен флаг `-u` в `git push -u origin main`?

Флаг `-u` (или `--set-upstream`) устанавливает связь между локальной веткой `main` и удаленной веткой `origin/main`. После этого можно писать просто `git push` и `git pull` без указания удаленного репозитория и ветки - Git будет знать, куда отправлять и откуда забирать. 

## 8. Что такое ветка (branch) по умолчанию и какая у вас создалась?

Ветка по умолчанию - основная ветка, в которой ведется разработка. Исторически Git создавал `master`, но с 2020 года GitHub и многие инструменты используют `main`.

При создании репозитория через веб-интерфейс GitHub у меня создалась ветка `main`.

Это важно, потому что от имени ветки зависит, куда будут отправляться изменения и как настроены CI/CD, защиты веток и т.д.

## 9. Как просмотреть историю коммитов и какую информацию о каждом коммите вы видите?

Команда: 

    git log 

Показывает: 
- хеш коммита (SHA-1);
- автора (имя и email);
- дату и время;
- сообщение коммита;

Для краткого вида: `git log --oneline`.
Для графического: `git log --graph --oneline --all`.

## 10. Что произойдет, если сделать изменения в файле, но не выполнить `git add` перед `git commit`?

Изменения останутся в рабочей папке, но не попадут в индекс. `git commit` зафиксирует только то, что уже было в индексе (если индекс не пуст) или выдаст ошибку "nothing to commit", если индекс пуст. Измененный файл останется в статусе "Changes not staged to commit" - то есть не будет включен в коммит.
