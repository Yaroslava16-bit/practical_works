# Ответы на вопросы — ПР21 (REST API)

## 1. Какие основные принципы REST архитектуры вы знаете?
1. **Ресурсо-ориентированность** (все сущности — это ресурсы, например, `/books`).
2. **Единообразие интерфейса** (использование стандартных HTTP-методов GET, POST, PUT, DELETE).
3. **Отсутствие состояния (Stateless)** (каждый запрос содержит всю необходимую информацию, сервер не хранит сессию клиента).
4. **Кэшируемость** (ответы сервера должны явно указывать, можно ли их кэшировать).

## 2. В чем разница между HTTP методами PUT и PATCH?
`PUT` используется для **полной** замены ресурса. Клиент должен отправить все поля объекта, даже если некоторые из них не изменились. `PATCH` используется для **частичного** обновления — клиент отправляет только те поля, которые нужно изменить.

## 3. Какие коды состояния HTTP наиболее часто используются в REST API?
- **200 OK** — успешный запрос (GET, PUT, PATCH, DELETE).
- **201 Created** — ресурс успешно создан (POST).
- **400 Bad Request** — ошибка в запросе клиента (например, не пройдена валидация).
- **404 Not Found** — ресурс не найден.
- **409 Conflict** — конфликт (например, дубликат уникального поля, как ISBN).
- **500 Internal Server Error** — ошибка на стороне сервера.

## 4. Что такое ресурсо-ориентированный дизайн URL?
Это когда URL проектируются как существительные (сущности), а действия над ними выражаются через HTTP-методы. 
*Плохо:* `/getBook?id=1`, `/deleteBook?id=1`. 
*Хорошо:* `GET /books/1`, `DELETE /books/1`.

## 5. Какие преимущества предоставляет пагинация в API?
Пагинация (разбиение на страницы, например, через `?page=1&limit=10`) позволяет не перегружать сеть и память сервера. Если в базе 10 000 книг, сервер не должен отправлять их все сразу. Пагинация ускоряет ответ и экономит трафик клиента.

## 6. Как организовать валидацию данных в REST API?
Валидация должна проводиться на сервере **до** сохранения данных. Можно использовать:
1. Ручную проверку (проверка наличия `title` и `author` через `if`).
2. Библиотеки валидации (Joi, express-validator, Yup).
При ошибке сервер возвращает статус `400 Bad Request` с описанием того, что именно не так.

## 7. Какие подходы к обработке ошибок в REST API вы знаете?
1. **Возврат правильных HTTP-статусов** (400, 404, 409, 500).
2. **Единый формат JSON для ошибок** (например, `{"error": "Описание ошибки"}`).
3. **Централизованный обработчик ошибок** (middleware с 4 аргументами в Express), который ловит все исключения и отправляет стандартный ответ (чтобы сервер не падал).

## 8. В чем разница между query parameters и path parameters?
- **Path parameters** (параметры пути) — являются частью URL и определяют конкретный ресурс: `/books/123`. В Express доступны через `req.params.id`.
- **Query parameters** (параметры запроса) — идут после знака `?` и используются для фильтрации, сортировки или пагинации: `/books?author=Иван&page=2`. В Express доступны через `req.query.author`.
